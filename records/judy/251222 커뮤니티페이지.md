## 1. 프로젝트 개요
Mr.PCPicker는 **Vue 3 + Django REST Framework** 기반의 PC 부품 커뮤니티 서비스입니다. 본 문서는 시스템을 구축하며 겪었던 시행착오와 기술적 해결 과정을 기록하기 위해 작성되었습니다.

---

## 2. 🚀 주요 난관 및 해결 과정 (Troubleshooting)

이 프로젝트를 진행하며 가장 어려웠던 부분은 **"데이터가 어디서 막혔는가?"**를 찾는 과정이었습니다.

### 2-1. [최대 난관] `user.user` 데이터 구조와 권한 제어
작성자 본인에게만 수정/삭제 버튼이 보여야 하는 로직에서 가장 큰 혼란이 있었습니다.
- **문제:** `localStorage.getItem('user')`를 통해 가져온 데이터가 단순한 정보가 아니라, 객체 안에 또 객체가 쌓여있는 구조(`{ user: { id: 1, ... }, access: "..." }`)였습니다.
- **원인:** 프론트엔드에서 `user.id`로 접근했으나 실제 데이터는 `user.user.id`에 위치하여 비교 연산이 항상 `false`가 됨.
- **해결:** `JSON.parse`를 통해 로컬 스토리지 구조를 정확히 분석한 뒤, **`parsed.user.id`**와 API 응답값의 작성자 ID를 매칭시켜 권한 제어를 완성했습니다.

### 2-2. 프론트 ↔ 백엔드 데이터 흐름의 불일치
초기 개발 시 에러가 발생하면 Vue의 문제인지 Django의 문제인지 구분하기 어려웠습니다.
- **상황:** URL 경로 불일치(`/community` vs `/articles`), Axios 요청 시점 오류, Serializer 검증 실패 등으로 인한 401/500 에러 빈번 발생.
- **해결:** * **브라우저 네트워크 탭**을 통해 백엔드로 요청이 전달되는지 먼저 확인.
  * Django 서버 로그를 통해 `no such table` 등의 DB 이슈(Migration 누락)를 파악하고 프론트 에러와 분리하여 생각하는 법을 익힘.

### 2-3. 인증 상태 관리 및 역할 분리
로그인 여부에 따라 UI가 실시간으로 변하지 않거나, 토큰 누락으로 요청이 거부되는 문제가 있었습니다.
- **해결:** * **Service:** API 통신(Axios) 로직 전담.
  * **Store (Pinia):** 로그인 여부 및 유저 정보를 전역 상태로 관리.
  * 역할 분리를 통해 "서버와 통신하는 법"과 "화면에 보여주는 법"을 독립적으로 설계했습니다.

## 3. 주요 기능 구현 상세

### 3-1. 커뮤니티 (게시판)
- **게시글 CRUD:** 목록 조회, 상세 보기, 작성, 수정, 삭제 기능 완비.
- **라우팅 에러 해결:** `:id` 파라미터가 포함된 수정 페이지(`PostEditView`)의 동적 라우트 등록 문제 해결.
- **댓글 시스템:** `flex` 레이아웃을 통해 작성자와 날짜를 양 끝으로 배치하여 시각적 안정성 확보.

### 3-2. 유저 시스템
- **프로필 커스터마이징:** 불필요한 '이름' 필드를 제거하고 '이메일' 필드 중심의 정보 관리.
- **입력 검증:** 이메일 미입력 시 `alert`를 띄워 필수 데이터 유실 방지.
- **개인화 섹션:** 장바구니 및 최근 본 상품 목록 데이터 바인딩 유지.

## 5. 💡 회고: "동작하는 코드에서 흐름이 보이는 구조로"
단순히 "동작하게 만드는 코드"를 넘어, 데이터가 컴포넌트에서 서비스로, 다시 백엔드 Serializer를 거쳐 DB에 저장되는 **전체 흐름(Full-Flow)**을 이해하는 계기가 되었습니다. 특히 백엔드 상태가 프론트에 미치는 영향을 추적하며 디버깅 역량이 크게 성장했습니다.
