Product Detail 을 '정규화 모델'로 만들기 위험 (애매하다)
- 같은 의미, 다른 키
- 구조 깊이도 다르고
- 타입이 섞여있고
- 데스크탑 / 노트북 / 올인원 만 있는 속성

- product_id, product_type, brand, model_name
- os, cpu_tier, gpu_tier, ram_gb, storage_gb, weight_kg, display_inch, price
- raw_json = JSONField()

- raw_json에 있어도 GMS가 “알아서 이해해서 추천”해주지는 않는다.

ETL 파이프라인
외부에서 온 데이터를 “서비스에서 쓰기 좋은 형태”로 바꿔서 저장하는 전체 과정
ETL = Extract · Transform · Load

1) Search로 ID 목록 만들고
2) Detail 호출해서 raw 저장하고
3) raw에서 spec 추출해 ProductSpec 업데이트

1️⃣ Extract (추출)
데이터를 가져오는 단계
TechSpecs Product Search API 호출
TechSpecs Product Detail API 호출
아직은 정제 안 된 원본 데이터
Search API → ProductSearch
Detail API → ProductDetailRaw.raw_json

2️⃣ Transform (변환)
쓸 수 있게 가공하는 단계 (가장 중요)

여기서 하는 일:
-키 이름 통일 (RAM, Capacity, Size → ram_gb)
-타입 통일 ("16 GB" → 16)
-불필요한 필드 제거
-의미 단위로 정규화 (OS, CPU, GPU, RAM…)
👉 네가 만든:
-detail_parser.extract_spec()
-raw_json → ProductDetailSpec
이 단계가 없으면:
-추천 불가
-검색 불가
-GMS 토큰 폭발

3️⃣ Load (적재)
변환된 데이터를 DB에 저장
-정규화된 컬럼을 가진 테이블에 저장
-인덱싱 가능
-빠른 검색 가능
👉 네 프로젝트에서:
ProductDetailSpec 테이블

Extract: TechSpecs API → raw_json
Transform: raw_json → 의미 있는 스펙(OS, RAM, GPU…)
Load: SQLite(ProductDetailSpec)

---

"추천 기반 DB”는 SQLite(=관계형 DB)로 만들고, “원본(raw) 보관용”은 JSON

✅ SQLite가 정답인 경우(너 케이스)
조건 검색이 많다: 예산, OS, RAM, GPU, 무게, 화면 크기 등으로 필터링/정렬
추천에서 “상위 N개” 뽑아야 한다: ORDER BY, LIMIT
데이터가 수천~수십만 건 가능
모델이 늘어도 안정적으로 운영하고 싶다
👉 너는 정확히 여기에 해당함.

✅ JSON이 맞는 경우(아주 제한적)
데이터가 아주 적다(수백 개 이하)
검색이 거의 없다(그냥 목록 보여주기 수준)
배포 시 “정적 파일”로만 쓰고 싶다
서버 없이 프론트에서만 읽는다
👉 너 서비스는 “추천/검색”이 핵심이라 JSON 단독은 곧 한계가 옴.
