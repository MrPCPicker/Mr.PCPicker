ETL 파이프라인
외부에서 온 데이터를 “서비스에서 쓰기 좋은 형태”로 바꿔서 저장하는 전체 과정
ETL = Extract · Transform · Load

1) Search로 ID 목록 만들고
2) Detail 호출해서 raw 저장하고
3) raw에서 spec 추출해 ProductSpec 업데이트

1️⃣ Extract (추출)
데이터를 가져오는 단계
TechSpecs Product Search API 호출
TechSpecs Product Detail API 호출
아직은 정제 안 된 원본 데이터
Search API → ProductSearch
Detail API → ProductDetailRaw.raw_json

2️⃣ Transform (변환)
쓸 수 있게 가공하는 단계 (가장 중요)

여기서 하는 일:
-키 이름 통일 (RAM, Capacity, Size → ram_gb)
-타입 통일 ("16 GB" → 16)
-불필요한 필드 제거
-의미 단위로 정규화 (OS, CPU, GPU, RAM…)
👉 네가 만든:
-detail_parser.extract_spec()
-raw_json → ProductDetailSpec
이 단계가 없으면:
-추천 불가
-검색 불가
-GMS 토큰 폭발

3️⃣ Load (적재)
변환된 데이터를 DB에 저장
-정규화된 컬럼을 가진 테이블에 저장
-인덱싱 가능
-빠른 검색 가능
👉 네 프로젝트에서:
ProductDetailSpec 테이블

Extract: TechSpecs API → raw_json
Transform: raw_json → 의미 있는 스펙(OS, RAM, GPU…)
Load: SQLite(ProductDetailSpec)

---

"추천 기반 DB”는 SQLite(=관계형 DB)로 만들고, “원본(raw) 보관용”은 JSON

✅ SQLite가 정답인 경우(너 케이스)
조건 검색이 많다: 예산, OS, RAM, GPU, 무게, 화면 크기 등으로 필터링/정렬
추천에서 “상위 N개” 뽑아야 한다: ORDER BY, LIMIT
데이터가 수천~수십만 건 가능
모델이 늘어도 안정적으로 운영하고 싶다
👉 너는 정확히 여기에 해당함.

✅ JSON이 맞는 경우(아주 제한적)
데이터가 아주 적다(수백 개 이하)
검색이 거의 없다(그냥 목록 보여주기 수준)
배포 시 “정적 파일”로만 쓰고 싶다
서버 없이 프론트에서만 읽는다
👉 너 서비스는 “추천/검색”이 핵심이라 JSON 단독은 곧 한계가 옴.

# TechSpecs API 데이터 수집 프로젝트

이 프로젝트는 **TechSpecs API**를 사용하여 제품 데이터를 수집하고, 해당 데이터를 **Django 모델**에 저장하는 작업을 기록한 내용입니다.

## 1. 목표
TechSpecs API를 통해 제품 데이터를 **400개**씩 순차적으로 받아오고, 이어서 **600개**, **400개**를 더 받아옵니다. 이 데이터를 `ProductSearch` 및 `ProductDetailRaw` 모델에 저장하는 작업을 진행합니다.

## 2. 설정
- **API URL**: `https://api.techspecs.io/v5/products/search`
- **헤더 설정**:
  - `X-API-KEY`: API 키
  - `X-API-ID`: API ID
  - `accept`: `application/json`

## 3. 데이터 수집

### 3.1 첫 400개 데이터 받기
- **요청 설정**: 한 페이지에 50개의 데이터를 받아오기 위해, `page = 0`부터 `page = 7`까지 총 8개의 페이지를 요청하여 400개의 제품 데이터를 수집합니다.
  
```python
for page in range(0, 8):
    params = {
        "query": category,
        "page": page,
        "size": 50,
        "keepCasing": "true"
    }
```

- **결과**: `ProductSearch` 모델에 400개의 데이터를 저장하고, 각 제품에 대해 상세 정보를 `ProductDetailRaw` 모델에 저장.

### 3.2 600개 데이터 추가 받기
- **요청 설정**: `page = 8`부터 `page = 19`까지 총 12개의 페이지를 요청하여 600개의 데이터를 추가로 받습니다.

```python
for page in range(8, 20):
    params = {
        "query": category,
        "page": page,
        "size": 50,
        "keepCasing": "true"
    }
```

- **결과**: `ProductSearch` 및 `ProductDetailRaw` 모델에 600개의 데이터를 추가로 저장.

### 3.3 400개 데이터 더 받기 (이어받기)
- **요청 설정**: 이미 600개의 데이터를 받은 상태에서, `page = 12`부터 `page = 19`까지 총 8개의 페이지를 요청하여 400개의 데이터를 더 받습니다.

```python
for page in range(12, 20):
    params = {
        "query": category,
        "page": page,
        "size": 50,
        "keepCasing": "true"
    }
```

- **결과**: `ProductSearch` 및 `ProductDetailRaw` 모델에 400개의 데이터를 추가로 저장.

## 4. 에러 처리

### 4.1 API 크레딧 한도 초과 (에러 402)
- **에러 메시지**: `Api limit reached. Please buy more credit to enjoy uninterrupted access to TechSpecs API`.
- **원인**: 현재 API의 무료 크레딧 한도가 소진되어 더 이상 요청을 보낼 수 없음.
- **해결 방법**:
  - **크레딧 구매**: 추가 크레딧을 구매하여 API 한도를 증가시켜야 함.
  - **고객 지원에 문의**: 결제 및 크레딧 추가 방법에 대해 문의.

## 5. 600개 데이터 이후 이어서 받기
- **목표**: 600개 데이터를 받았으므로, 400개를 더 받기 위해 **560 크레딧**이 필요.
- **설정**:
  - 한 페이지당 **50개**의 데이터가 요청되며, 400개를 받으려면 **8페이지**가 필요.
  - 1페이지당 **70 크레딧** 소모 시, 총 **560 크레딧**이 필요.

- **결과**: 560 크레딧이면 400개의 추가 데이터를 받을 수 있음.
